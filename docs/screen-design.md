## 2. STEP2の目的と対象範囲

### 2.1 目的

- MatchupLabのブランドとローカルファーストの利用モデルを画面上で一貫して示す。
- メンバー登録から対戦表作成、結果確認、PDF出力までの導線を短くする。
- PC、タブレット、スマートフォンで、入力・結果・エラー・ダイアログが欠落しない画面構造を確定する。
- 非同期処理、空データ、入力不足、復元失敗などの状態を、画面の見た目だけで判別できるようにする。

### 2.2 STEP2に含めるもの

- アプリシェル、ヘッダー、ナビゲーション、現在地表示。
- ホーム画面、メンバー管理画面、ダブルス条件・結果画面、シングルス条件・結果画面。
- JSONバックアップ操作の画面状態と復元確認ダイアログ。
- 参加者選択、コート数調整、エラー表示、生成中表示、PDF出力状態。
- PC／タブレット／スマートフォンのレイアウト切り替え。
- オフライン表示とService Worker更新通知の表示領域。
- MatchupLab向けの表示文言、プレースホルダー、空状態文言。

### 2.3 STEP2に含めないもの

- Firebase、認証、アカウント管理、既存データ移行。
- 組合せ生成アルゴリズム、`generateDraw()` 相当のドメイン処理の変更。
- 新しい競技形式、スコア管理、過去結果の永続化。
- メンバーJSON以外のバックアップ形式。
- 実機・クロスブラウザー・性能計測を完了条件とすること。これらはPhase 3で実施する。ただしSTEP2では、検証可能な画面状態と証跡取得方法を準備する。

## 3. 設計原則

### 3.1 利用モデル

- 保存先は「この端末」に限定する。画面では、技術用語の「IndexedDB」ではなく「この端末に保存」を使う。
- ネットワーク接続やアカウントの有無に依存せず、メンバー管理、組合せ生成、PDF出力を使える状態を基本とする。
- ヘッダーにはアカウント作成、ログイン、ログアウトを表示しない。
- 保存中・復元中・生成中は、対象操作を二重実行できないようにする。

### 3.2 情報設計

- 1画面につき主要操作を1つにする。
- 主要操作はパネル内で最も視認性の高い位置に置く。
- 空状態は「利用できない」ではなく、「次に何をすればよいか」を示す。
- エラーは操作対象の近くに表示し、画面上部だけの一時通知に依存しない。
- ホバー時だけ意味が分かる操作を作らない。フォーカス、タッチ、キーボードでも同じ情報を得られるようにする。

### 3.3 既存実装との境界

STEP2では、現在の `AppClientShell` に集約されている責務を、次の画面単位へ分割しやすい構造にする。ただし、画面分割のためにデータモデルやドメイン境界を変更しない。

| 現在の責務 | STEP2の画面／コンポーネント境界 |
| --- | --- |
| `AppHeaderNav` | `AppShell`、`Header`、`PrimaryNav` |
| `LandingHomeScreen` | `HomeScreen` |
| `MemberManagementScreen` | `MembersScreen`、`MemberBackupPanel`、`MemberFormPanel`、`MemberListPanel` |
| `MatchupScreen` | `MatchupScreen`、`MatchupConditionPanel`、`MatchupResultPanel` |
| `CourtReductionDialog` | `CourtReductionDialog` |
| 参加者選択、人数入力、並び替え | `ParticipantSelector`、`CountStepperField`、`SortModeSelect` |
| オフライン／更新状態 | `PwaStatus` |

### 3.4 現行実装（2026-10-06）

実装根拠は `src/app/AppClientShell.tsx`、`src/app/globals.css`、`src/components/pwa/PwaStatus.tsx` とする。

#### 画面・ナビゲーション

| 画面／部位 | 現行の表示・操作 |
| --- | --- |
| `/` | 登録メンバー人数、メンバー管理・ダブルス・シングルスへの3つのカード。「メンバー登録（ローカル保存）」を表示 |
| ヘッダー | MatchupLabとアイコン。PCはホーム・メンバー・対戦表メニュー、対戦表配下から形式別URLへ遷移 |
| モバイルメニュー | 860px以下でメニューボタンを表示。背景操作・Escape・リンク選択で閉じ、開いている間は背景スクロールをロック |
| `/members` | メンバー一覧と登録順／アイウエオ順切替、バックアップ、復元、新規追加。行メニューから編集・削除 |
| 登録・編集 | 一覧とは別のアプリ内ダイアログ。ニックネーム（表示名）必須・画面入力10文字まで、氏名、性別、備考。登録／更新・キャンセル |
| 削除 | 「メンバーを削除します」ダイアログ。確認後に完全削除し、キャンセル・Escape・背景操作では取り消す。非表示・再表示UIはない |
| JSON復元 | ファイル検証後にアプリ内確認ダイアログを表示。既存メンバーの全置換と個人情報を案内し、成功時は件数を3秒の通知で表示 |
| `/matchups/doubles` | 開催名、通常／同性対決優先／混合対決優先、メンバー選択、コート数、実施回数、人数集計、「対戦表作成」 |
| `/matchups/singles` | ダブルスと同様の条件欄。対戦モードの選択欄はなく通常固定 |
| 結果 | ラウンドごとのコートカードと休憩者。結果に「PDF作成」ボタン。空の開催名は画面で「対戦表」、PDFで「MatchupLab」 |

#### 参加者と画面状態

- 参加者ダイアログでは登録メンバーの個別選択・全選択・全解除と女性／男性のゲスト人数を操作する。OKで確定し、キャンセルで仮入力を破棄する。合計30人を超える確定はエラーにする。
- メンバーを登録せずゲストだけでも利用できる。Guestログイン・アカウント画面は提供しない。
- コート数は1〜8面、実施回数は1〜20回。開催名初期値は空、実施回数初期値は4回。人数不足・不正条件は作成ボタンを無効化する。
- 人数に対してコートが過剰なときは「コート数を調整します」を表示し、使用可能面数への減算を確認する。キャンセルでは生成しない。
- 生成成功は「対戦表作成が完了しました。」を3秒の通知で表示する。再生成は同じ「対戦表作成」の再押下で行う。
- ダブルスとシングルスの条件・仮選択・確定選択・結果はAppClientShellの形式別メモリー状態に保持する。ルート移動で維持し、再読み込みで初期化する。
- メンバー削除・復元後は存在しないactive IDを両形式の選択から除く。表示中の生成済み結果は参加者のスナップショットとして残る。
- PDF出力中はボタンを無効化し「PDF出力中...」を表示する。失敗は結果パネルに表示する。
- メンバー保存・復元には共通のbusyフラグがなく、すべての操作の二重実行防止を保証しているわけではない。同期生成の処理中表示についても描画・応答性を別途検証する。

#### レスポンシブ・アクセシビリティ

- 主なCSS境界は1120px、860px、359px。PCのメンバー一覧は列見出し付き、狭幅ではカード状に表示する。
- 860px以下では並び順とバックアップ・復元・新規追加を1行に並べ、操作ボタンを幅36pxのアイコン表示にする。PCではテキストラベルを表示する。
- これらの操作は `aria-label` と `title` を保持し、装飾アイコンは `aria-hidden="true"` とする。
- ダイアログにはrole・aria-modal・見出し参照を設定する。全ダイアログのフォーカストラップ・復帰、ブラウザの戻る操作による閉鎖、全コントロール44px以上、reduced-motion対応を検証済みとはしない。

#### PWA表示

- オフラインでは「オフラインで利用中」を表示する。
- 更新可能なら通知と「更新」ボタンを表示する。「後で」ボタンはない。
- 利用者が更新するとWorkerの切替後にページを再読み込みする。条件・結果などの一時状態は失われる。
- 保存・復元中の更新禁止や更新応答のタイムアウトはない。Service Worker登録・キャッシュ成功を示す専用の準備完了表示もない。

以下の章は当初案・受入観点として保持する。現在の画面との差分は上記と [実装状況](./implementation-status.md) に記載した内容を優先する。

## 5. 画面別設計

### 5.1 ホーム画面 `/`

#### 目的

初回利用者が、メンバー登録から対戦表作成までの手順を理解し、現在の登録状態に応じた次の操作へ進めるようにする。

#### 構成

```text
┌─────────────────────────────────────────────┐
│ MatchupLab                                   │
│ 対戦表をかんたんに作成                       │
│ [メンバーを管理] [対戦表を作成]              │
├─────────────────────────────────────────────┤
│ メンバー                                     │
│ 12人がこの端末に保存されています             │
├─────────────────────────────────────────────┤
│ 使い方                                       │
│ 1. メンバーを登録  2. 条件を入力  3. 作成     │
├──────────────────────┬──────────────────────┤
│ ダブルス             │ シングルス             │
│ 条件を入力して作成   │ 条件を入力して作成     │
│ [作成する]           │ [作成する]             │
└──────────────────────┴──────────────────────┘
```

| 要素 | 設計 |
| --- | --- |
| ヒーロー | アプリの目的を1〜2行で示す。固定のテニス大会名やサンプルイベント名は使わない |
| メンバー概要 | 登録人数を表示。「0人」の場合はメンバー登録への導線を優先表示 |
| 利用手順 | メンバー登録、条件入力、対戦表作成の3段階を簡潔に示す |
| 形式カード | ダブルス、シングルスの2カード。カード全体を押せるようにせず、主ボタンを明示する |
| 主要操作 | メンバーが0人なら「メンバーを登録」、1人以上なら「対戦表を作成」を優先する |

#### 状態

| 状態 | 表示・操作 |
| --- | --- |
| 初期化中 | メンバー人数領域に読み込み中表示。操作可能な固定部分は表示する |
| メンバー0人 | 「まだメンバーが登録されていません」と表示し、`/members`へ誘導する |
| メンバー1人以上 | 登録人数とダブルス／シングルスへの導線を表示する |
| 読み込み失敗 | 人数を推測表示せず、再読み込みまたはメンバー画面への導線を表示する |

### 5.2 メンバー管理画面 `/members`

#### 目的

この端末に保存するメンバーを管理し、JSONファイルによる手動バックアップ・全置換復元を安全に行う。

#### デスクトップ構成

```text
┌─────────────────────────────────────────────────────────────┐
│ メンバー管理                                                  │
│ この端末に保存されます                                        │
├─────────────────────────────────────────────────────────────┤
│ JSONバックアップ                                               │
│ [JSONをダウンロード]  [JSONを読み込む]                         │
│ 形式、保存先、復元時の全置換を短く説明                         │
├──────────────────────────────┬──────────────────────────────┤
│ メンバーを登録                 │ 登録済みメンバー               │
│ 名前 [                    ]    │ 12人                           │
│ 性別 [                    ]    │ [並び順 ▼]                    │
│ [登録する]                     │ 佐藤  [編集] [非表示]          │
│                                │ 鈴木  [編集] [非表示]          │
└──────────────────────────────┴──────────────────────────────┘
```

#### 構成要素

| 要素 | 設計 |
| --- | --- |
| ページ見出し | 「メンバー管理」。保存先を補足文で「この端末」と示す |
| JSONバックアップパネル | ページ上部に配置し、ダウンロードと読み込みを隣接させる |
| 登録フォーム | 名前、必要な属性、登録ボタン。入力エラーは各入力の直下に表示する |
| メンバー一覧 | 人数、並び替え、編集、非表示を提供する。非表示状態は一覧から判別できる |
| 空状態 | 「登録済みメンバーはいません」と表示し、フォームへ視線を誘導する |
| 復元説明 | 「読み込んだ内容で、この端末のメンバーを置き換えます」と明示する |

#### JSON操作の状態

| 状態 | 表示・操作 |
| --- | --- |
| 通常 | ダウンロード／読み込みを使用できる |
| 出力中 | ダウンロードボタンを無効化し、完了後に成功表示を出す |
| 出力成功 | ファイル名と「ダウンロードしました」を表示する |
| ファイル選択中 | 選択されたファイル名を表示し、読み込み処理へ進む |
| 復元確認 | 件数と「既存メンバーを全置換する」ことを確認できるダイアログを表示する |
| 復元中 | 読み込みボタンとメンバー編集操作を無効化する |
| 復元成功 | 置換後の件数を表示し、一覧を再読込する |
| JSON不正 | JSON形式、スキーマ、必須項目のどこで失敗したかを示し、既存データを変更しない |
| 復元失敗 | 既存データを変更しなかったことを示し、再選択できる |
| 0件復元 | 有効な全置換として扱い、一覧を空状態にする |

### 5.3 対戦表条件画面 `/matchups/doubles`、`/matchups/singles`

#### 目的

形式ごとの条件を入力し、入力内容を確認してからローカルで対戦表を作成する。

#### 構成

```text
┌─────────────────────────────────────────────────────────────┐
│ ダブルス対戦表                                                │
│ 条件を入力して対戦表を作成                                   │
├─────────────────────────────────────────────────────────────┤
│ 1. 基本情報                                                   │
│ 開催名 [午後の対戦会                                  ]      │
├──────────────────────────────┬──────────────────────────────┤
│ 2. 参加者                     │ 3. コート・ラウンド            │
│ [登録メンバーを選ぶ ▼]        │ コート数 [−] 2 [+]             │
│ 一時参加者 [−] 0 [+]          │ ラウンド数 [−] 3 [+]           │
│ 選択中: 8人                    │                              │
├──────────────────────────────┴──────────────────────────────┤
│ 確認: 8人 / 2コート / 3ラウンド                                │
│ [対戦表を作成する]                                             │
└─────────────────────────────────────────────────────────────┘
```

シングルスでも同じ画面構造を使い、見出し、選択肢、説明文、結果表示だけを形式に合わせて切り替える。入力項目の位置を形式ごとに変えない。

#### 入力項目

| 項目 | 設計 |
| --- | --- |
| 形式 | 画面見出しと現在地で明示する。ダブルス／シングルスの切替はナビゲーションから行う |
| 開催名 | 任意入力。例は一般的な対戦会名とし、特定競技・固定イベントに依存しない |
| 登録メンバー | メンバー選択ダイアログまたはポップオーバー。選択人数と未選択人数を表示する |
| 一時参加者 | Guestとして現在の機能を維持する。登録メンバーと区別して表示する |
| コート数 | ステッパー。現在値、最小値、最大値、利用可能なコート数を判別できるようにする |
| ラウンド数 | ステッパー。現在値、最小値、最大値を判別できるようにする |
| 確認サマリー | 参加者、コート、ラウンド、形式を作成ボタンの近くに表示する |
| 主要操作 | 「対戦表を作成する」。入力不備または処理中は無効化する |

#### 条件入力の状態

| 状態 | 表示・操作 |
| --- | --- |
| 初期化中 | メンバー選択を読み込み中にし、生成操作を無効化する |
| 入力可能 | 各項目を編集でき、サマリーを更新する |
| 参加者0人 | 「参加者を1人以上選択してください」と表示し、生成不可 |
| 必要人数未満 | 形式に必要な人数を満たすまでエラーを表示し、生成不可 |
| 上限30人 | 30人を選択できる。31人目は選択できず、上限を説明する |
| コート数が利用可能数超過 | 自動的に減らさず、減らす必要がある場合は確認ダイアログを表示する |
| コート数が最小／最大 | ステッパーの該当ボタンを無効化し、値を範囲内に保つ |
| ラウンド数が最小／最大 | ステッパーの該当ボタンを無効化し、値を範囲内に保つ |
| 生成中 | 作成ボタンを無効化し、処理中であることを表示する |
| 生成失敗 | 入力値を保持したまま、原因と再試行操作を表示する |

### 5.4 参加者選択

参加者選択は、候補一覧と現在の選択状態を同時に確認できる操作とする。

```text
┌─────────────────────────────────────────────┐
│ 参加者を選択                                  │
│ [名前で絞り込む                         ]     │
│ ☑ 佐藤   ☑ 鈴木   ☐ 高橋   ☐ 田中             │
│ 選択中 8人                                     │
│                         [キャンセル] [決定]     │
└─────────────────────────────────────────────┘
```

- 開く前に、現在の選択人数をボタンのラベルまたは補足に表示する。
- 0件、検索結果0件、30人上限、選択済みの状態を区別する。
- 決定前の一時選択は、キャンセルで元の選択へ戻す。
- キーボード操作では、開く、候補移動、選択、決定、キャンセルの順に操作できる。
- モバイルでは画面幅に合わせたダイアログとし、背後の条件入力を誤操作できないようにする。

### 5.5 コート数調整ダイアログ

参加者数に対して指定コート数が使用できない場合は、暗黙に値を変更せず、理由と変更後の値を確認させる。

```text
┌─────────────────────────────────────────────┐
│ コート数を調整します                          │
│ 参加者数に対して、指定したコート数は           │
│ 使用できません。                               │
│ 使用可能なコート数: 2                          │
│                                               │
│ [キャンセル]             [2コートに変更]        │
└─────────────────────────────────────────────┘
```

- キャンセル時は条件入力画面を保持する。
- 確定時だけコート数を更新し、確認サマリーも更新する。
- ダイアログ表示中は背後の生成操作を実行できない。
- Escapeキー、背景クリック、画面戻る操作の扱いを統一し、誤確定を起こさない。

### 5.6 対戦表結果画面

結果は条件入力画面の下部に表示し、条件を見直してから再生成できる構成にする。結果をIndexedDBへ保存する機能は追加しない。

```text
┌─────────────────────────────────────────────────────────────┐
│ 作成結果                                                       │
│ 午後の対戦会 / ダブルス / 8人 / 2コート / 3ラウンド            │
│ [PDFをダウンロード] [条件を変えて再作成]                       │
├──────────────────────┬──────────────────────┬────────────────┤
│ 第1ラウンド           │ 第2ラウンド           │ 休憩            │
│ コート1               │ コート1               │ 佐藤             │
│ A - B                 │ C - D                 │ 鈴木             │
│ ...                   │ ...                   │ ...             │
└──────────────────────┴──────────────────────┴────────────────┘
```

| 状態 | 表示・操作 |
| --- | --- |
| 結果なし | 条件入力を優先表示し、結果パネルは表示しない |
| 結果あり | 開催名、形式、人数、コート数、ラウンド数を結果見出しに表示する |
| PDF出力中 | PDFボタンを無効化し、出力中表示を出す |
| PDF出力成功 | ダウンロード完了を表示し、結果を保持する |
| PDF出力失敗 | 結果を消さず、再試行できるエラーを表示する |
| 再生成 | 入力条件を保持し、生成中は旧結果の操作を無効化する。成功後に結果を置き換える |

#### 結果の表示原則

- ラウンド、コート、対戦、休憩者の階層を視覚的に分ける。
- 小さい画面で横スクロールを強制しない。ラウンドまたはコートを縦方向に積める構造を基本とする。
- PDFボタンは結果見出しの近くに置くが、画面幅が狭い場合は結果見出しの下へ移す。
- 生成結果の表示名は、現在のドメインモデルと `buildBracketViewModel()` 相当の表示境界を維持する。

## 6. 共通ダイアログ・通知設計

| 種類 | 用途 | 必須状態 |
| --- | --- | --- |
| 確認ダイアログ | JSON復元の全置換、コート数変更 | 開く、キャンセル、確定、処理中、失敗 |
| 選択ダイアログ | 登録メンバー選択 | 開く、検索、0件、上限、キャンセル、決定 |
| インラインエラー | 入力項目や処理対象の近くに原因を示す | 未入力、範囲外、形式不正、処理失敗 |
| 成功通知 | 保存、JSON出力、JSON復元、PDF出力 | 成功内容と対象件数／ファイルを示す |
| PWA状態表示 | オフライン、更新、更新失敗 | 状態を混同しない |

共通ルール:

- ダイアログ表示時はフォーカスをダイアログ内へ移し、終了時に起点へ戻す。
- `role="dialog"`、ラベル、説明、閉じる操作を設定する。
- 破壊的または全置換の操作は、ボタン名に具体的な結果を含める。例: 「メンバーを置き換える」。
- 成功通知だけで重要な結果を伝えず、画面上にも状態を残す。
- 自動消滅する通知は、読み上げやキーボード操作を妨げない補助情報に限定する。

## 7. レスポンシブ設計

### 7.1 ブレークポイント

既存 `globals.css` の画面切り替え（1120px、860px、359px）をSTEP2の初期基準とし、DrawLabのデスクトップ／モバイル切替の考え方を取り込む。

| 区分 | viewport | レイアウト |
| --- | --- | --- |
| ワイドデスクトップ | 1121px以上 | ヘッダー内ナビゲーション、複数カラム、結果カード横並び |
| コンパクトデスクトップ／タブレット横 | 861〜1120px | 条件入力を2列まで縮小、長い項目は全幅 |
| モバイル | 360〜860px | ヘッダーメニュー、パネル縦積み、結果を縦方向に展開 |
| 狭幅モバイル | 359px以下 | 参加者サマリーなどを1列化。横スクロールを発生させない |

### 7.2 共通寸法方針

- コンテンツの最大幅は約1280pxとし、広い画面では左右の余白を均等にする。
- デスクトップの外側余白は24〜28px、モバイルは16〜18pxを基準にする。
- パネル間の余白は16〜24px、パネル内の項目間は8〜16pxを基準にする。
- ボタンと入力の最小高さは44pxを基準とし、タッチで押しやすい領域を確保する。
- 角丸、境界線、影はカード・入力・ダイアログで一貫させる。DrawLabのカード／フォーム体系を参考にするが、色はMatchupLabのブランドに合わせて再調整する。
- `prefers-reduced-motion: reduce` では画面遷移や通知のアニメーションを抑制する。

### 7.3 画面別の切り替え

| 画面 | デスクトップ | モバイル |
| --- | --- | --- |
| ホーム | ヒーローと形式カードを横並び | ヒーロー、概要、形式カードを縦積み |
| メンバー | バックアップ全幅、フォーム／一覧の2列 | バックアップ、フォーム、一覧の順に縦積み |
| 条件入力 | 条件パネルを2〜3列、サマリーを下部 | 1列。各入力の説明を入力直下に置く |
| 参加者選択 | 中央ダイアログ、候補を複数列にできる | 画面幅に合わせた1列または2列ダイアログ |
| 結果 | ラウンド／コートを複数列 | ラウンド／コートを縦積み。PDF操作は見出し下へ移動 |
| PWA状態 | 画面上部または右上の補助バナー | 画面幅を使うインラインバナー |

### 7.4 レスポンシブ受入条件

- 320px相当の狭幅でも、入力名、エラーメッセージ、主要ボタン、ダイアログ操作が欠けない。
- 375px、390px、768px、1024px、1280pxの代表幅で水平スクロールが発生しない。
- キーボード表示を想定して、入力中に固定要素が主要操作を覆わない。
- モバイルのメニュー、ダイアログ、通知が背後の操作を誤って受け取らない。
- PDF出力ボタン、JSON復元ボタン、生成ボタンは、表示幅に関係なく見つけられる。

## 8. 文言設計

### 8.1 用語

| 用途 | 採用文言 | 避ける文言 |
| --- | --- | --- |
| 保存先 | この端末に保存 | IndexedDBに保存、クラウドに保存 |
| 保存状態 | ローカル保存 | Firebase保存、サーバー保存 |
| JSON復元 | JSONを読み込む／メンバーを置き換える | インポートだけで結果が分からない表現 |
| 生成 | 対戦表を作成する | APIを呼び出す、生成リクエストを送る |
| 結果出力 | PDFをダウンロード | サーバーでPDF生成 |
| 参加者 | 登録メンバー／一時参加者 | 認証ユーザー |

### 8.2 固定文言の方針

- ブランド名は `MatchupLab` に統一する。
- `Tennis Organizing App` など旧ブランド名を画面、manifest、PDF、JSONファイル名に残さない。
- 特定の大会名や「週末テニス会」のような固定イベント文言をプレースホルダーにしない。
- ダブルス／シングルスは現行機能の形式名として維持する。ただし、説明文は特定の競技施設や大会運営を前提にしない。
- エラーは「できません」だけで終わらず、修正方法を含める。

## 9. 画面状態モデル

すべての非同期操作は、少なくとも「初期化中」「入力可能」「処理中」「成功」「失敗」を区別する。画面をまたぐデータは必要最小限にし、メンバーはIndexedDB、組合せ結果は画面メモリとして扱う。

```text
初期化中 ──成功──> 入力可能 ──主要操作──> 処理中
   │                  │                     │
   └─失敗────────────> 失敗 <────失敗────────┘
                         │
                         └─再試行──> 入力可能
```

### 9.1 データ状態と画面表示

| データ状態 | 画面表示 | 禁止する誤認 |
| --- | --- | --- |
| メンバー未読込 | 読み込み中 | 0人と断定する |
| メンバー0件 | 空状態、登録導線 | 読み込み失敗と混同する |
| メンバーあり | 一覧と件数 | 保存済みか不明にする |
| JSON選択済み未検証 | ファイル名、検証中 | 即時に既存データを置換する |
| JSON検証成功未確定 | 件数と全置換確認 | 追加処理と誤認させる |
| JSON検証失敗 | エラー、既存データ維持 | 部分的に復元されたと見せる |
| 組合せ結果あり | 結果カード、PDF操作 | リロード後も保存されると誤認させる |

## 10. テスト設計の先行定義

STEP2では、画面実装前に次の観点をテスト設計の基準とする。テストケースを増やす前に、各ケースが何を検証するかを明記する。

### 10.1 テスト観点

| 観点 | 確認内容 |
| --- | --- |
| 機能 | ルート遷移、メンバー操作、JSON操作、条件入力、生成、PDF出力が設計どおり動く |
| UI | 現在地、主要操作、空状態、エラー、処理中、成功が視認できる |
| データ | 読み込み前と0件、JSON全置換、失敗時の既存データ保持、結果の非永続性を区別する |
| 非機能 | オフライン、更新通知、キーボード、読み上げ、狭幅、Reduced Motionで破綻しない |
| 状態遷移 | 初期化中→入力可能→処理中→成功／失敗→再試行の遷移が競合なく成立する |
| 環境差異 | Chromiumを初期検証対象とし、Phase 3でモバイル実機、Firefox、WebKitを追加する |

### 10.2 正常系・異常系・境界値・状態遷移

| 分類 | 対象 | 検証意図 |
| --- | --- | --- |
| 正常系 | メンバー登録→対戦表作成→PDF出力 | 主導線が最後まで途切れないことを確認する |
| 正常系 | JSON出力→選択→全置換復元 | 既に確認済みのSTEP1データ境界を画面から壊さないことを確認する |
| 異常系 | 不正JSON、必須項目不足、IndexedDBエラー、PDFエラー | 既存データや入力条件を失わず、再試行できることを確認する |
| 異常系 | 参加者不足、コート超過、範囲外入力 | 生成前に原因を示し、無効な処理を開始しないことを確認する |
| 境界値 | 0人、必要人数未満、30人、31人、コート数1／8、ラウンド数1／20 | 上限・下限・空状態の表示と操作制御を確認する |
| 状態遷移 | 生成中の連打、復元中の画面遷移、更新中の再操作 | 二重実行、競合、途中状態の表示崩れを確認する |
| UI境界 | 320、375、390、768、1024、1280px | テキスト、ボタン、ダイアログ、PDF操作が欠けないことを確認する |

### 10.3 E2E実施範囲

STEP2の初回受入では、画面構造と状態表示のリスクに絞り、Chromiumで対象導線を実行する。全件E2Eを既定にはしない。

- 実施する: `/`→`/members`→`/matchups/doubles` の主要遷移、空状態、登録、生成、JSON復元ダイアログ、生成中／失敗表示の確認。
- 実施する: 代表 viewportでのスクリーンショット、コンソールエラー確認、ダイアログのフォーカス確認。
- 実施しない: STEP2の画面変更だけではリスクが増えないドメイン単体テストの全件再設計。
- Phase 3へ回す: 実機、Firefox、WebKit、長時間負荷、Service Worker更新の実環境確認。
- 同一実機への自動化スクリプトは並列実行しない。各テストはデータ初期化または独立したブラウザコンテキストを前提とする。
- 失敗時は、viewport、オンライン／オフライン、事前データ件数、操作順、コンソールログ、スクリーンショットを証跡として残す。

## 11. 実装時の受入基準

- 4ルートが同じアプリシェルと現在地表示を共有している。
- アカウント、Firebase、外部APIを示すUIがない。
- ホーム、メンバー管理、ダブルス、シングルスの各画面が本書の構成と状態を満たす。
- JSON復元は、確認、全置換、成功、失敗、0件の状態を区別して表示する。
- 参加者不足、上限超過、コート数調整、生成中、生成失敗、PDF出力失敗を画面上で判別できる。
- 360px以上のモバイル幅で横スクロールを発生させず、359px以下でも主要操作が欠けない。
- キーボード操作、フォーカス表示、ダイアログのフォーカストラップ、Reduced Motionに対応する。
- UI変更後も、Phase 1で確認済みのJSON読み込み・復元、ローカル生成、オフライン利用、PDF出力を壊さない。
- 実装差分、未実施ブラウザー、未確認端末、既知の制約をPhase 2の検証記録へ追記する。

## 12. 次の実装単位

画面設計を次の順序で実装する。

1. アプリシェル、ヘッダー、ナビゲーション、共通パネル、PWA状態表示。
2. ホーム画面とメンバー管理画面の構造分割・文言整理。
3. 対戦表条件画面、参加者選択、コート数調整ダイアログ。
4. 結果パネル、PDF操作、生成中・失敗状態。
5. レスポンシブCSS、キーボード／ダイアログアクセシビリティ、代表viewport検証。

この順序では、先に共通シェルと状態表示を固定し、その後に各機能画面を分割する。組合せロジック、IndexedDB、JSON境界は既存実装を利用し、STEP2の画面変更から独立させる。

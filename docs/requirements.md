## 2. 目的と基本方針

### 2.1 目的

メンバー管理とコート／ラケット競技の組合せ作成を、アカウント、クラウド保存、外部APIなしで利用できるローカルファースト型アプリとして提供する。

### 2.2 基本方針

- メンバーデータはブラウザのIndexedDBへ保存する。
- 組合せ生成はブラウザ内の純粋ロジックを直接呼び出す。
- 組合せ作成、PDF出力、JSONバックアップ・復元はネットワーク切断中も利用できるようにする。
- 保存するのはメンバーデータのみとし、画面入力途中の状態と組合せ結果は永続化しない。
- JSONバックアップは利用者が自分で管理する一般的なテキストファイルとする。
- UIは `draw-lab` の設計思想を参考にするが、コンポーネントや画面構成を無条件にコピーしない。
- 初期対象は、1対1または2対2で行うコート／ラケット競技とする。3対3以上のチーム競技は対象外とする。

## 3. テスト設計の前提

テストケースを作成する前に、次の観点を確認する。各ケースには「何を検証するか」という意図を記載する。

### 3.1 観点一覧

| 観点 | 検証対象 |
| --- | --- |
| 機能 | メンバー管理、参加者選択、Guest、条件入力、組合せ、再作成、PDF、JSON、オフライン |
| 非機能 | 生成性能、メインスレッド停止、PWA更新、アクセシビリティ、ブラウザ差異、個人情報保護 |
| データ | IndexedDB保持、スキーマ更新、JSON検証、全置換、トランザクション、データ消失説明 |
| UI | 空状態、入力エラー、処理中、二重実行、成功・失敗表示、フォーカス、レスポンシブ表示 |

### 3.2 ケース分類

- 正常系：通常のメンバー、参加者、コート数、実施回数で最後まで完了する。
- 異常系：不正JSON、未対応スキーマ、IndexedDBエラー、生成エラー、容量超過、更新失敗を扱う。
- 境界値：0人、形式ごとの最小人数、最大30人、最大8面、最大20回、奇数人数を扱う。
- 状態遷移：初回起動、保存後の再読み込み、オンライン／オフライン、生成中、復元確認、Service Worker更新を扱う。

### 3.3 前提条件

- テストごとにIndexedDBを初期化できる。
- JSONテストデータは正常、空、破損、未対応バージョン、重複ID、型不正を用意する。
- 同一seedの再現性テストでは `generatedAt` などの非決定的項目を比較対象から除外する。
- E2Eではネットワーク状態、ブラウザ、viewport、PWAインストール状態を明示する。
- 同一実機に対するE2Eスクリプトは並列実行しない。

## 4. 対象利用者と利用シナリオ

### 4.1 主な利用者

練習会やサークルの主催者が、自分のPCまたはスマートフォンでメンバーを管理し、当日の参加者から組合せを作成する。

### 4.2 代表シナリオ

1. 初回アクセス後、メンバーを登録する。
2. 次回アクセス時、同じブラウザ・端末のIndexedDBからメンバーを表示する。
3. 当日の参加者とGuest人数を入力する。
4. シングルスまたはダブルス、コート数、実施回数、対戦モードを指定する。
5. 組合せを作成し、結果を確認して必要なら再作成する。
6. 結果をPDF出力する。
7. 端末変更やサイトデータ削除に備え、メンバーJSONを出力・復元する。

## 5. 機能要件

### 5.1 アプリ起動・認証

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-001 | ログイン画面を経由せずホーム画面を表示できる | 必須 |
| FR-002 | Firebase Authentication、Guestログイン、ログアウト、パスワード再設定を提供しない | 必須 |
| FR-003 | 認証状態やユーザーIDによるデータ分離を行わない | 必須 |
| FR-004 | Firebase関連の環境変数なしで開発サーバーと本番ビルドを実行できる | 必須 |

### 5.2 メンバー管理

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-010 | メンバーを登録できる | 必須 |
| FR-011 | メンバーを編集できる | 必須 |
| FR-012 | 確認ダイアログの承認後、メンバーをIndexedDBから完全削除する。キャンセル時は変更しない | 必須 |
| FR-013 | 登録順と読み仮名順で一覧を切り替えられる | 必須 |
| FR-014 | 有効メンバーは99人を上限とする | 高 |
| FR-015 | ブラウザ再読み込み後も登録済みメンバーを復元する | 必須 |
| FR-016 | IndexedDB操作失敗時に利用者向けエラーを表示し、入力内容を可能な限り保持する | 必須 |

メンバーの保存項目は、ID、ニックネーム、氏名、性別、備考、読み仮名、状態、表示順、登録日時、更新日時、任意の非表示日時とする。ニックネームは必須とし、前後空白を除去する。画面入力の上限は10文字だが、repositoryとJSON境界では文字数上限を検証しない。氏名・備考は任意、性別は女性／男性、読み仮名は自動生成する。

新規登録は `active` とする。JSON互換性のため `inactive` と `deactivatedAt` は保持するが、現行UIに非表示化・再表示操作はない。削除されたレコードは削除前のバックアップの全置換復元でのみ戻せる。

### 5.3 参加者選択とGuest

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-020 | 有効メンバーから当日の参加者を選択できる | 必須 |
| FR-021 | 選択解除、全選択、選択確定、キャンセルを操作できる | 必須 |
| FR-022 | Guest人数を女性・男性に分けて入力できる | 必須 |
| FR-023 | 登録メンバーとGuestを合わせた参加者数を表示する | 必須 |
| FR-024 | 参加者数が30人を超える入力を拒否する | 必須 |
| FR-025 | GuestをメンバーデータとしてIndexedDBへ保存しない | 必須 |

Guestは匿名ログインではなく当日だけの一時参加者を意味する。登録メンバー0人でもGuestだけで生成できる。女性から先に `ゲスト01` から採番し、男性は続く番号にする。選択と人数入力はOKで確定し、キャンセルで破棄する。全選択後も合計30人の検証を行う。

### 5.4 組合せ条件

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-030 | 開催名を入力できる。テニス固有の固定初期値は使用しない | 必須 |
| FR-031 | シングルス／ダブルスを切り替えられる | 必須 |
| FR-032 | ダブルスでは通常、同性対決優先、混合対決優先を選択できる | 必須 |
| FR-033 | シングルスでは対戦モードを表示せず、通常条件で生成する | 必須 |
| FR-034 | コート数を1〜8面で入力できる | 必須 |
| FR-035 | 実施回数を1〜20回で入力できる | 必須 |
| FR-036 | 参加者数に対してコート数が過剰な場合、使用可能面数への調整確認を表示する | 必須 |
| FR-037 | シングルスは2人以上、ダブルスは4人以上を必要とする | 必須 |

### 5.5 組合せ生成

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-040 | 組合せ作成時にサーバー、Firebase、外部APIへ通信しない | 必須 |
| FR-041 | 組合せ生成ロジックをReact、Next.js、Firebaseから独立した純粋関数として呼び出す | 必須 |
| FR-042 | 同一入力と同一seedから同一の組合せを再現できる | 必須 |
| FR-043 | 複数候補seedを評価し、基準ロジックと同じ優先順位で最良結果を選択する | 必須 |
| FR-044 | 休憩回数、連続休憩、顔合わせ、同一ペア、同一対戦相手、性別優先を評価する | 必須 |
| FR-045 | 生成中は処理中表示を行い、二重実行を防止する | 必須 |
| FR-046 | 生成失敗時に再試行可能なエラーを表示する | 必須 |
| FR-047 | 再作成では新しいseedを使う | 必須 |

再作成は「対戦表作成」ボタンの再押下で行い、専用の再作成ボタンやseed指定UIは提供しない。生成はメインスレッド上の同期処理であり、処理中状態はあるが描画や操作応答性の性能保証は未確認である。

### 5.6 結果表示とPDF

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-050 | ラウンド、コート、対戦者、休憩者を表示する | 必須 |
| FR-051 | シングルスは1対1、ダブルスはペアA／ペアBとして表示する | 必須 |
| FR-052 | 結果には採用seedを保持する。結果自体は永続化しない | 高 |
| FR-053 | 現在表示中の結果をPDF出力できる | 必須 |
| FR-054 | PDFは組合せ作成後、ネットワーク切断中でも出力できる | 必須 |
| FR-055 | PDF内のアプリ名・固定文言をMatchupLabの表記へ統一する | 必須 |

### 5.7 JSONバックアップ・復元

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-060 | IndexedDBに残る全メンバー（JSON復元したinactiveも含む）を単一JSONへ出力する。完全削除したレコードは含まない | 必須 |
| FR-061 | JSONに `schemaVersion`、`appVersion`、`exportedAt`、`members` を含める | 必須 |
| FR-062 | JSONファイル名を `matchuplab-members-YYYY-MM-DD.json` とする。日付は出力時のUTC日付 | 必須 |
| FR-063 | JSON形式、スキーマバージョン、必須項目、型、重複IDを読み込み前に検証する | 必須 |
| FR-064 | 不正JSON、未対応バージョン、検証失敗時に既存IndexedDBを変更しない | 必須 |
| FR-065 | 復元前に全置換の確認ダイアログを表示する | 必須 |
| FR-066 | 復元は既存メンバーの全置換とし、部分的なマージを行わない | 必須 |
| FR-067 | 復元成功後に復元件数を表示する | 必須 |
| FR-068 | JSONに氏名・性別・備考が含まれることを画面上で案内する | 必須 |
| FR-069 | JSONバックアップの暗号化は本フェーズの対象外とする | 対象外 |

スキーマは `schemaVersion: 1`、有効人数上限は99人とする。日時項目は非空文字列として検証し、ISO形式・日時の妥当性までは検証しない。復元件数はinactiveを含む総件数であり、一覧・参加者選択にはactiveだけを表示する。

### 5.8 オフライン・PWA

| ID | 要件 | 優先度 |
| --- | --- | --- |
| FR-070 | 本番モードでService Workerを登録し、ルートHTML・manifest・アイコン・PDFフォントを事前キャッシュする | 必須 |
| FR-071 | 必要なHTML・JavaScript・CSS等の取得とキャッシュが成功したアプリをネットワーク切断後に起動できる | 必須 |
| FR-072 | 必要な資産を取得済みなら、オフラインでメンバー表示・登録・編集・完全削除・参加者選択ができる | 必須 |
| FR-073 | オフラインで組合せ作成、再作成、結果表示、PDF、JSON入出力ができる | 必須 |
| FR-074 | キャッシュ名をバージョン管理し、不要な旧キャッシュを削除する | 必須 |
| FR-075 | APIレスポンスや個人データをService Workerの静的キャッシュへ保存しない | 必須 |

開発モードではService Workerを自動登録しない。Next.js静的チャンクは実際の取得時にキャッシュするため、初回ページを開くだけで全資産の準備が完了するとは限らない。更新通知の「更新」で待機中Workerを有効化し再読み込みする。更新時はメンバー以外の一時状態を失う。キャッシュ失敗の案内や処理中の更新禁止は未実装であり、詳細は [設計書](./design.md#9-pwaオフライン設計) を参照する。

## 6. データ要件

### 6.1 Member型

```ts
type Gender = "female" | "male";
type MemberStatus = "active" | "inactive";

type Member = {
  id: string;
  nickname: string;
  fullName: string;
  gender: Gender;
  note: string;
  sortKeyKana: string;
  status: MemberStatus;
  displayOrder: number;
  createdAt: string;
  updatedAt: string;
  deactivatedAt?: string;
};
```

### 6.2 永続化しないデータ

次のデータはIndexedDBおよびJSONバックアップへ保存しない。

- 開催名
- 選択中メンバー
- Guest人数
- コート数、実施回数、対戦モード
- 生成結果、生成履歴、PDF出力履歴
- 画面の一時入力状態

ページ再読み込み後はメンバーだけを復元し、入力途中の条件と結果は初期状態へ戻す。

### 6.3 データ保全

- IndexedDBのトランザクション失敗時は、旧データを維持する。
- JSON復元は検証完了後に1つのreadwriteトランザクションで全置換する。
- ブラウザ、端末、プロファイル、オリジンの変更やサイトデータ削除でデータへアクセスできなくなる可能性を案内する。
- 自動アップロード、クラウド同期、外部バックアップは行わない。

## 7. 非機能要件

### 7.1 プライバシーとセキュリティ

- 組合せ作成、メンバー操作、JSON処理で外部通信しない。
- Firebase SDK、Firebase環境変数、外部組合せAPIキーを完成状態に残さない。
- 個人情報をURL、ログ、解析サービス、Service Workerキャッシュへ含めない。
- JSONは暗号化されないため、利用者自身が安全に管理する旨を表示する。
- ローカル保存は同じブラウザプロファイルを利用できる人から保護されない。この制約をプライバシー説明に含める。

### 7.2 性能

暫定受入基準として、最大条件（30人、8面、20回）を各形式・各対戦モードで測定する。

- PCのp95生成時間：3秒以内
- スマートフォンのp95生成時間：5秒以内
- 生成中に操作不能となる長時間停止を発生させない
- 基準値を超える場合はWeb Worker化を別タスクではなく性能対策として再評価する

測定端末、ブラウザ、入力seed、候補seed数、結果を記録し、単発の最速値では判定しない。

### 7.3 対応環境

リリース判定では、Chromium系デスクトップとiOS Safariの実機確認を必須とする。Firefox等は追加確認対象とし、未確認の場合は対応保証を表示しない。

### 7.4 アクセシビリティ

- キーボード操作でフォーカス位置を確認できる。
- ダイアログ、メニュー、ドロップダウンの開閉とEscape操作が成立する。
- エラー、成功、処理中、無効状態を色だけに依存せず伝える。
- `prefers-reduced-motion` が有効な場合、不要なアニメーションを抑制する。

## 8. UI要件

現行画面は [画面設計書の現行実装](./screen-design.md#34-現行実装2026-10-06) を参照する。同書の他の節はSTEP2当初の改善案を含み、すべての実装完了を意味しない。

対象画面は `/`、`/members`、`/matchups/doubles`、`/matchups/singles` とする。

- アプリ名、マニフェスト、PDF、JSONファイル名、キャッシュ名をMatchupLabへ統一する。
- 「IndexedDB」ではなく「この端末に保存」など利用者向けの表現を使用する。
- テニス固有の固定文言を削除し、開催名や競技名を利用者が理解できる表現にする。
- `draw-lab` の色、余白、カード、フォーム、ナビゲーションの設計思想を参考にする。
- メンバー0件、参加者不足、コート数過多、生成中、生成失敗、復元確認、復元成功を明確に表示する。
- 画面幅が狭い場合でも、入力欄、結果カード、ダイアログ、PDFボタンが操作可能である。

## 9. 対象外

- Firebaseデータの自動移行
- クラウド保存、複数端末同期、共同編集、共有URL
- ユーザーアカウント、ログイン、監査ログ、API利用ログ
- 組合せ履歴、入力途中条件、PDF履歴の永続化
- 暗号化バックアップ
- 3対3以上のチーム競技
- ネイティブアプリ化
- 本フェーズでのNext.jsからViteへの移行

### 11.3 フェーズ間のゲート

- Phase 0からPhase 1へ進む前に、移植元コミット、依存関係、現行テストの結果を固定する。
